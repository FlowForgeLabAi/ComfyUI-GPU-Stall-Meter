# ComfyUI GPU Stall Meter

[English](README.md) | 简体中文

GPU 利用率只告诉你「SM 在忙」，它不告诉你**在忙什么**。

当工作流卡在主机内存换页上时，利用率会一直顶在 99–100%，而 GPU 其实在等页面从磁盘换进来。
工具栏上每个表看起来都健康，进度条一动不动，而常见的那句建议（「GPU 都跑满了，再给它点活干」）
恰好是反的。这两种状态只能靠利用率以外的信号区分。

这个包把那些信号做成画布里的一个小面板：**显卡功耗**、**SM 时钟**、**主机内存压力**，
以及由它们推出的**停滞判定**。

## 显示什么

| 读数 | 来源 | 用来看什么 |
|---|---|---|
| `PWR` | NVML `nvmlDeviceGetPowerUsage` | 瓦。GPU 在等而不是在算的时候，它会塌下去 |
| `CLK` | NVML `nvmlDeviceGetClockInfo(SM)` | 兆赫。SM 被饿住时会掉到几百 |
| `RAM` | psutil | 主机可用内存。模型比内存大是最常见的原因 |
| 状态 | 推导 | `idle` / `ok` / `stalled` / `calibrating` |

面板停在 ComfyUI 那条浮动工具条的下面、画布的上方。它是 `pointer-events: none`，所以鼠标点它
会**穿透到下面的节点** —— 代价是它不能被悬停；判定理由（写明当时的功耗、时钟和可用内存）会在
停滞刚开始时以通知的形式弹出。

## 为什么看功耗和时钟，而不是利用率

在一台机器上实测（RTX 5060 Laptop，8 GB 显存 / 16 GB 内存）跑 MiniMax-H3，与真实生成循环
并行采了 **534 个样本**：

| 信号 | 健康 | 换页停滞中 |
|---|---|---|
| `utilization.gpu` | 99–100% | **99–100%，毫无变化** |
| 板卡功耗 | 64–98 W | **平在 34–36 W** |
| SM 时钟 | ~2760 MHz | **最低掉到 180 MHz** |
| 可用主机内存 | — | **中位数 1.92 GB**（共 15.26 GiB） |
| 页面文件余量 | — | **中位数 6.89 GB** |

整个采样期间板卡功耗的**中位数是 32.8 W** —— 也就是说在那台机器上，停滞状态是**常态而不是极端情况**。
工作集约 34.5 GiB（主模型 19.5 GiB + nvfp4 文本编码器 14.96 GiB），而可用内存只有 15.26 GiB。

原始数据：<https://huggingface.co/datasets/FlowForgeLabAi/minimax-h3-8gb-bench>
（`h3_monitor_log.csv`，534 行 × 13 列，10 秒一个点）。

## 停滞判定怎么算

阈值是**相对于这张卡、这次会话**的，因为一块笔记本 5060 和一块台式 4090 的绝对瓦数没法直接比：

1. 运行期间，面板记录每个 GPU **见过的最高功耗**与**最高 SM 时钟**，以及当时的可用内存。
2. **预热 30 个样本**之后判定才开始生效。
3. 以下条件**同时成立**时才报 `stalled`：
   - 利用率 ≥ 80%，**且**
   - 功耗 ≤ 本次会话最高值的 50%，**且**
   - 可用主机内存 ≤ 总量的 10%，**且**
   - SM 时钟 ≤ 本次会话最高值的 60%（时钟可读时）。
4. 其余情况：利用率高时报 `ok`，利用率低时报 `idle`。

**内存那条是让判定保持诚实的关键。** 一个小工作流完全可以合理地跑在 99% 利用率、低功耗上而毫无问题；
真正让这个状态病态的是 GPU 在等页面文件。四个阈值都是设置项，不是写死的常数。

## 停滞时自动中断（默认关闭）

一个停滞的跑批可能就那么挂着几小时什么也不产出 —— 上面那台机器上，同一个工作流健康时跑
34–44 分钟，换页时要**大约十二小时**。这个包可以替你中断它，并且在动手之前刻意设了几道闸：

- **默认关闭。** 判定可能出错，而中断会牺牲已经跑掉的那部分。
- 判定必须**连续成立**满设定的秒数（默认 60 秒），不是看到一帧就动手。
- 只在队列里**确实有任务在跑**时动手，且**每分钟最多一次**。
- 中断时会弹通知，写明触发它的功耗、时钟和可用内存。

打开这个开关还会让面板在**浏览器标签页切到后台时继续轮询**；否则隐藏标签页会暂停轮询 ——
因为盯着它有一点成本，而看不到的时候盯着没有意义。

## 安装

手动：克隆或解压到 `ComfyUI/custom_nodes/`，重启 ComfyUI。**唯一必需的依赖是 `psutil`**，
绝大多数 ComfyUI 环境里本来就有。NVML 在装了 `pynvml` 时走它，没装就用 `ctypes` 直接调显卡驱动
自带的 `nvml.dll` / `libnvidia-ml.so.1` —— 所以这个包**不额外安装任何东西**。

等第一次发布到注册表之后，ComfyUI Manager 里搜 `GPU Stall Meter` 也能找到。

## 设置项

在 `Settings > GPU Stall Meter` 下：

| 设置 | 默认 | 说明 |
|---|---|---|
| 读数开关 | 开 | 关掉只隐藏面板；采样路由仍然可用 |
| 采样间隔 | 1000 ms | 每次轮询是一次 NVML 读取 |
| 最低利用率 | 80% | 低于它就报 idle，不做判定 |
| 功耗比上限 | 0.5 | 相对本次会话见过的最高值 |
| 时钟比上限 | 0.6 | 相对本次会话见过的最高值 |
| 可用内存比上限 | 0.10 | 相对主机内存总量 |
| 停滞时中断跑批 | 关 | 见上文 |
| 连续停滞多少秒后中断 | 60 | 判定需要先连续成立这么久 |

## 局限 —— 提 issue 之前请先读这段

- 它**检测**停滞，不修复停滞。修复办法是缩小工作集：更短的片子、更低的分辨率、更小的文本编码器，
  或者加内存。
- 绝对瓦数因卡而异。判定会自校准，但每次会话的**前 30 个样本**它还在学这张卡，那段时间只会是
  `ok`/`idle`。
- `nvmlDeviceGetPowerUsage` 并非所有卡都支持（某些 vGPU 和数据中心配置会直接抛错）。那种情况下
  `PWR` 读数显示为不可用，判定退化为「内存压力 + 时钟」。
- AMD 和 Apple 显卡没有 NVML。面板会报告没找到 NVIDIA GPU，其余什么都不会发生。
- 上面那些数字来自**一台**机器。它们是阈值的起点，不是定律。
